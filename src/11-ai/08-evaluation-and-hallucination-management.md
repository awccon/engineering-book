# Evaluation and Hallucination Management

How do you know Beacon's reply drafts are good? That the help assistant doesn't invent
answers? That the new prompt is better than the old one, or that switching to a cheaper model
didn't quietly hurt quality? With traditional code, tests answer such questions. With LLM
features, outputs vary, "correct" is often a matter of degree, and failures are subtle. Without
deliberate **evaluation**, teams ship on vibes: a few examples look good in a demo, and quality
problems surface as customer complaints.

Evaluation is the discipline that turns AI features from demos into engineering. This chapter
covers how to build evaluation sets, measure quality (with code, humans and LLM judges), manage
hallucinations, and wire evaluation into CI and production monitoring.

---

## 1. The problem: you can't unit-test a vibe

Traditional tests assert exact outputs. AI outputs:

- vary between runs,
- can be correct in many different wordings,
- can be fluent and wrong,
- change when the model, prompt, retrieval or data changes, often in unexpected places.

Yet you still need answers to: *Is it good enough to ship? Did this change make it better or worse?
Is it degrading in production?*

---

## 2. The mental model: evals are test suites for behavior

```text
 Evaluation set (inputs + expectations)  ──►  system under test (prompt + model + retrieval + code)
                                                        │
                                                        ▼
                                                    outputs
                                                        │
             ┌──────────────────────────────────────────┼─────────────────────────────┐
             ▼                                          ▼                             ▼
   code-based checks                          model-graded checks                human review
   (format, citations, rules,                 (LLM-as-judge with rubric:         (gold standard;
    exact labels, latency, cost)               correctness, groundedness,         calibrates the others)
                                               tone, helpfulness)
             └──────────────────────────────────────────┴─────────────────────────────┘
                                                        │
                                                        ▼
                                    scores per case and aggregate metrics
                                    compared against baseline and thresholds
```

> **🧱 Durable:** Define what "good" means **before** building the feature, as concrete criteria
> and examples agreed with the people who'll use it. An evaluation set is the specification of an AI
> feature.

## 3. Building evaluation sets

### Sources of cases

- **Real data** (sanitized): historical tickets, real customer questions, past incidents. The most
  representative source.
- **Expert-written cases** for important scenarios and edge cases.
- **Production failures**: every reported bad output becomes a case (the AI equivalent of a regression
  test; Book I, Chapter 14).
- **Synthetic cases** generated by a model (variations, adversarial inputs, rare categories). Useful to
  expand coverage; review them, because they tend to be easier and more uniform than reality.

### What a case contains

```json
{
  "id": "help-047",
  "input": { "question": "Laptop drops the work network about every hour (Windows 11)", "tenant": "acme" },
  "expected": {
    "must_cite_any_of": ["kb-112"],
    "answerable": true,
    "key_points": ["renew the VPN certificate", "update the VPN client to 5.2 or later"],
    "must_not": ["promise a refund", "mention another customer"]
  },
  "tags": ["network", "paraphrase", "windows"]
}
```

Expectations are often **criteria**, not exact answers: required facts, required citations, forbidden
content, whether the question is answerable at all.

### Size and coverage

- Start with **20–50** cases; that already catches most regressions. Grow to hundreds for mature
  features.
- **Cover the distribution and the edges**: common questions, rare categories, other languages,
  unanswerable questions, ambiguous questions, adversarial inputs (Chapter 9), long inputs.
- **Tag cases** to see where quality differs ("non-English answers are 15 points worse").
- **Keep a held-out set** you don't tune against, to detect overfitting the prompt to the eval set.

## 4. Measuring: code, judges and humans

### Code-based checks (cheap, deterministic, use them first)

| Check | Example |
|---|---|
| Format and schema | Output parses as `TicketClassification` |
| Exact labels | Classification matches expert label (accuracy, precision/recall per class) |
| Citations | All citations refer to provided sources; required source cited |
| Rules | No forbidden phrases; length within limits; correct language |
| Retrieval | Recall@k, MRR for the retrieval step (Chapter 5) |
| Operational | Latency, input/output tokens, cost per case, tool call counts |

### LLM-as-judge

For qualities code can't check (correctness against key points, faithfulness to sources, helpfulness,
tone), a model can grade outputs against a **rubric**:

```text
You are grading a support answer. Use only the sources and the reference key points.

<sources>...</sources>
<key_points>...</key_points>
<answer>...</answer>

For each criterion, give PASS or FAIL with a one-sentence reason:
1. Grounded: every factual claim in the answer is supported by the sources.
2. Complete: the answer covers all key points.
3. Safe: no promises of refunds, credits or deadlines.
Return JSON: {"grounded": {...}, "complete": {...}, "safe": {...}}
```

Making judges reliable:

- **Specific, binary or small-scale criteria** (pass/fail, 1–3) rather than vague 1–10 scores.
- **Give the judge the reference material** (sources, key points); judging "is this correct?" without
  references is unreliable.
- **Calibrate against humans**: have experts grade 50–100 cases; measure judge agreement; refine the
  rubric until agreement is high.
- **Watch judge biases**: preference for longer answers, for their own model family's style, for the
  first of two options in pairwise comparisons (randomize order).
- Use a **strong model** as judge, and keep the judge prompt and model fixed when comparing versions.

### Human review

The gold standard, and the source of truth for calibrating everything else. Use humans for: defining
criteria, labeling the eval set, calibrating judges, reviewing samples of production output, and making
launch decisions. Make reviewing easy (a simple tool showing input, sources, output and rubric).

### Comparing versions

- **Same eval set, same judge**, run the baseline and the candidate.
- Look at **aggregate metrics and per-case diffs**: which cases got worse? A higher average can hide
  new severe failures.
- **Run multiple samples** for noisy metrics (outputs vary); small differences may be noise.
- Track **cost and latency** alongside quality: a change that adds 2% quality for 3× cost may not be worth it.

## 5. Hallucinations: understanding and managing them

A **hallucination** is output that is fluent and confident but not supported by facts or the provided
context. Kinds:

| Kind | Example |
|---|---|
| **Fabricated facts** | An invented setting name, a non-existent API method, a fake policy |
| **Unfaithful to context** | The source says "version 5.2"; the answer says "5.0" |
| **Invented citations** | `[kb-301]` that doesn't exist, or exists but doesn't say that |
| **Overreach** | Answering a question the sources don't cover, from general knowledge |
| **Reasoning errors** | Wrong date math, wrong conclusion from correct facts |

Why they happen (Chapter 1): models generate plausible continuations; they're trained to be helpful and
rarely to say "I don't know"; their knowledge is lossy; and missing or wrong retrieval leaves gaps they
fill with plausible text.

### A layered defense

| Layer | Technique | Chapter |
|---|---|---|
| **Task design** | Use AI where errors are tolerable or reviewable; keep humans on consequential decisions | 1, 4 |
| **Grounding** | RAG with good retrieval; tools for live data; don't ask the model to recall facts | 4, 6 |
| **Prompting** | "Use only the sources," explicit "I don't know" path, citations required | 3, 6 |
| **Constrained output** | Schemas, enums, allowed values | 4 |
| **Verification** | Citation checks in code; groundedness checks by a judge model; cross-checking numbers and IDs against data | 6, this chapter |
| **Computation in code** | Dates, sums, SLAs computed by code, not the model | 1 |
| **UX** | Show sources; label AI output; make correction and escalation easy | 6, 10 |
| **Monitoring** | Sample and grade production outputs; user feedback; alerts on drift | this chapter |

No single layer eliminates hallucinations. Together they reduce frequency and, crucially, **make the
remaining errors visible and recoverable**.

> **⚠️ What can go wrong:** Asking the model "are you sure?" or "rate your confidence" doesn't reliably
> catch its own hallucinations. Verification must use **external evidence**: the sources, the database,
> code checks, or a separate judge given the references.

## 6. Evaluation in the development workflow

### Offline evaluation in CI

```text
 PR changes prompt / model / retrieval / chunking
   └─► CI: run eval suite for affected features (subset on every PR, full set nightly)
        └─► report: metrics vs main, per-case regressions, cost/latency deltas
             └─► gate: fail if key metrics drop below thresholds; otherwise attach report for review
```

Eval runs cost money and time; balance by running a fast, high-signal subset on PRs and the full set
nightly or before releases.

### Online evaluation in production

- **Sampling**: grade a random sample of production interactions daily with the judge, plus human review
  of a smaller sample.
- **User signals**: thumbs up/down, edits to drafts (how much did the agent change the AI draft?),
  escalations to human agents, "didn't help" clicks.
- **A/B tests** for prompt or model changes on real traffic, with quality and business metrics.
- **Drift monitoring**: quality metrics over time; changes in input distribution (new products, new
  languages) that the eval set doesn't cover.

Feed production failures back into the eval set: the loop that makes AI features improve over time.

## 7. In practice: Beacon's evaluation harness

The harness lives in `tools/beacon-tools/evals` (Python, Book X), because the evaluation ecosystem is
richest there, and calls Beacon's AI features through an internal evaluation endpoint (or directly
through the same prompt templates and model configuration).

### Structure

```text
evals/
  datasets/
    classification.jsonl       200 tickets with expert labels (area, urgency)
    help_assistant.jsonl       150 questions: answerable/unanswerable, key points, required sources
    reply_draft.jsonl           60 threads with expert notes
    incident_agent.jsonl        15 historical incidents with expert-linked tickets
  judges/
    grounded_complete_safe.md  rubric prompt (calibrated against two experts' grades on 80 cases)
  run_eval.py                  runs a dataset against a target config, stores results
  compare.py                   diffs two runs: metrics, per-case regressions, cost/latency
```

### A run

```bash
uv run python -m evals.run_eval --dataset help_assistant --target staging --prompt HelpAnswer.v5 --samples 2
uv run python -m evals.compare runs/help_assistant/main.json runs/help_assistant/HelpAnswer.v5.json
```

Illustrative output:

```text
help_assistant: HelpAnswer.v4 (main) vs HelpAnswer.v5
  retrieval recall@6          93.1% → 93.1%   (=)
  grounded (judge)            94.7% → 97.3%   (+2.6)
  complete (judge)            86.0% → 85.3%   (-0.7, within noise)
  safe (judge + rules)        99.3% → 100%    (+0.7)
  abstains when unanswerable  89.5% → 92.1%   (+2.6)
  citation validity (code)    98.0% → 99.3%   (+1.3)
  mean output tokens          142 → 131
  cost per 1k questions       (unchanged within 3%)
  regressions: 3 cases (help-018, help-092, help-133) → see report
```

The PR includes this report. Reviewers read the three regressed cases before approving: one is a real
regression (fixed with an example), two are judge disagreements on borderline cases (noted).

### Thresholds (CI gate for the help assistant)

| Metric | Gate |
|---|---|
| Citation validity | ≥ 98% |
| Safe | 100% |
| Grounded | ≥ 95% |
| Abstains when unanswerable | ≥ 85% |
| Any metric drop vs main | ≤ 2 points without explicit sign-off |

### Production monitoring

- Nightly job samples 200 assistant conversations (with consent and redaction, Chapter 9) and grades
  them; a dashboard tracks grounded/safe/abstain rates over time (Book IX, Chapter 6).
- Reply drafts: the **edit distance** between AI draft and sent reply is tracked per agent and team; a
  sudden increase suggests quality dropped.
- Thumbs-down and "didn't help" cases are queued for weekly human review and added to datasets.

## 8. What can go wrong

- **Shipping on demos**: a few hand-picked examples instead of an eval set.
- **Eval sets that don't reflect reality** (too easy, synthetic only, missing languages and edge cases).
- **Overfitting prompts to the eval set**, without a held-out set.
- **Uncalibrated LLM judges** treated as ground truth.
- **Averages hiding severe regressions.**
- **Ignoring cost and latency** in comparisons.
- **No production monitoring**: quality drifts as inputs, models and content change.
- **Self-verification by asking the same model** whether it's sure.

---

## 9. How an experienced engineer thinks about this

- **The eval set is the spec.** Build it with domain experts before and during development.
- **Code checks first, judges second, humans to calibrate.**
- **Every change is an experiment**: compare against a baseline, inspect per-case regressions.
- **Hallucinations are managed in layers**, and the remaining errors must be visible and recoverable.
- **Close the loop**: production failures become test cases.

## 10. Check yourself

**Questions**

1. Why can't AI features be tested with exact-output unit tests alone?
2. What should an evaluation case contain? Where do good cases come from?
3. When would you use code checks, LLM judges and human review?
4. How do you make an LLM judge reliable?
5. What are the main kinds of hallucination? Why do they occur?
6. Describe a layered defense against hallucinations.
7. How do offline and online evaluation differ, and how do they feed each other?

**Exercises**

1. Build a 30-case eval set for ticket classification from realistic tickets and measure accuracy and a
   confusion matrix.
2. Write a groundedness judge rubric, grade 30 answers yourself, and measure the judge's agreement with
   you.
3. Add an eval step to CI that runs 20 cases on PRs touching prompts and posts a comparison report.
4. Collect ten bad outputs from a feature you use, categorize the failure types, and propose a layer that
   would catch each.

**Interview-style questions**

- "How do you evaluate the quality of an LLM-powered feature?"
- "How do you reduce hallucinations?"
- "What is LLM-as-a-judge, and what are its pitfalls?"
